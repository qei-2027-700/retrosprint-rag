# ADR-0006: アプリのDBにPostgreSQLを採用する

- 決定日：2026年10月18日
- 状態：accepted（DB製品の採用方針。テーブル設計・実装は未完了）
- 関連：[開発計画 #1](https://github.com/qei-2027-700/retrosprint-rag/issues/1)

## 背景

文書の状態、利用者、会話・メッセージ、引用、非同期ジョブ等のアプリデータを保存する必要がある。従来の資料ではDynamoDBを含む構成案があったが、DBは未決定としていた。

2026年10月18日に、本人からPostgreSQLを使う想定が示された。

## 選択肢

| 選択肢 | 扱い |
| --- | --- |
| PostgreSQL | 今回採用するアプリのDB |
| DynamoDB | 以前の構成案。アプリの標準DBとしては採用しない |

## 決定と理由

本人の希望に基づき、アプリのDBにPostgreSQLを採用する。性能・費用の比較で優位と実証した判断ではなく、以後のAPI・データ設計の前提とする技術選定である。

AWS上の配置先、PostgreSQLの版、ORM・DBドライバー、マイグレーションツール、接続管理、テーブル構造は未決定。RDSやAurora等のサービスを今回の決定だけで採用済みとは扱わない。

文書本文・ファイルの保存先、Bedrock、S3 Vectors、Cognitoの採用方針は維持する。PostgreSQLを選んだことだけでベクトル検索をpgvectorへ置き換えない。BigQueryはETL成果物のデータ源として引き続き検討する。

## 影響とトレードオフ

旧資料のDynamoDB固有のテーブル・キー・トランザクション・Streamsの設計を、そのまま実装仕様にはしない。認可、状態遷移、重複防止、配送失敗の回復、削除競合の要件は維持し、PostgreSQLを前提に保存・更新・配送の方法を設計し直す。

テーブルは機能仕様とAPIの操作・状態・所有者・削除範囲を確認してから決める。DBと外部サービスをまたぐ処理の整合性、マイグレーション、バックアップ・復旧、接続数、配置費用を検討する必要がある。

## 検証方法と現在の結果

採用方針の文書化までで、テーブル・マイグレーション・DB接続は未実装。

実装時にはマイグレーションとDB接続、所有者や状態の制約、トランザクション、重複・同時更新・削除競合、配送失敗からの回復を確認する。ローカルの検証とAWS上の接続・運用検証を分けて記録する。

## 再検討条件

配置費用、接続・運用上の制約、データ要件に合わないことが分かった場合に再検討する。変更は新しいADRとAPI・データ設計へ反映する。
