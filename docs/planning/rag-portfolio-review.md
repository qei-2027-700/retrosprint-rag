# RAGポートフォリオ設計・計画レビュー

実施日：2026-10-12。対象：[実行計画](rag-portfolio-plan.md)、今回作成した[詳細設計](rag-portfolio-design.md)。

## 判定

元の計画は機能の方向性を示していたが、同期生成の実行制限、token失効、配送失敗、ファイル差し替え、削除競合について実装判断が不足していた。そのまま実装に進むことは推奨しない。

今回、下記の指摘を設計に反映し、API契約・データモデル・セキュリティ・障害時の動作を詳細設計へ追加した。リポジトリの雛形と段階1の検証を開始できる状態と判断する。AWSでの成立と実装の安全性はまだ確認しておらず、公開可能という判定ではない。

優先度はP0＝採用構成の成立・認可・データ漏えいに関わる問題、P1＝障害時の整合性・悪用・運用に関わる問題、P2＝品質と公開説明の改善とする。「反映済み」は文書の修正を指し、実装検証の完了を意味しない。

## P0：実装前に解消する問題

| ID | 指摘・影響 | 反映した設計 | 実装時の確認 |
| --- | --- | --- | --- |
| R01 | HTTP APIの30秒制限に対し、同期のモデル生成が長引くと回答が取得できない | 202でjob受付、SQS chat worker、結果取得のポーリング | 30秒を超えるfake生成と実AWS経路で履歴再開まで確認 |
| R02 | JWTの署名・期限だけではCognitoで失効したtokenや旧admin権限を拒否できない | 現在のUsers状態とgroup照合、アプリ側セッション失効、ロール変更手順 | 旧token・利用停止・ログアウト・別client・ID tokenを拒否 |
| R03 | 文書・会話・jobをIDだけで取得すると権限を迂回できる | 全保護APIとworkerでrole/owner/stateを検証。共有文書の範囲も定義 | admin/user双方で他ユーザーIDへ差し替えて拒否を確認 |
| R04 | アップロード完了後も署名付き送信を再利用でき、確認したファイルを差し替えられる | サイズを制約したPOST、quarantine、version固定、公開用領域の分離 | 同じ署名条件で上書きしても固定版だけが取り込まれる |

## P1：整合性・セキュリティ・運用

| ID | 指摘・影響 | 反映した設計 | 実装時の確認 |
| --- | --- | --- | --- |
| R05 | DB保存とqueue送信の間の障害でjobが永久に止まる | transaction + outbox、Streams dispatcher、未配送の回復処理 | 保存直後・配送直後に障害を注入して同一jobを回復 |
| R06 | SQS重複・同時送信で二重メッセージ・同時生成・過剰課金が起きる | idempotency、入力hash、lease、会話単位のactive job | 同一key同一/別入力、重複配信、同時送信を確認 |
| R07 | モデルの呼び出し結果が不明な障害で自動再試行すると課金が重複する | invokingを記録し、結果不明はoutcome_unknown。自動再生成を止める | model呼び出し後・結果保存前の停止で再生成しない |
| R08 | 取り込みや生成と削除が競合し、文書が復活したり削除後に回答が公開される | tombstone、処理世代、完了transaction、manifest先行保存、旧worker終了後の再掃除 | 削除中のready復帰と回答保存を拒否し、残存データを回収 |
| R09 | ファイル形式の偽装・破損・巨大な抽出結果でworkerが停止する | 形式許可リスト、実内容検証、容量・ページ・文字・チャンク・時間上限 | 偽装、暗号化・破損PDF、抽出上限、期限切れuploadを確認 |
| R10 | 原文の命令、モデル生成HTML、危険なリンクが漏えいやXSSにつながる | 取得文書をデータとして扱い、管理ツールを与えない。Markdown sanitize、raw HTML・リモート画像等を制限 | 悪意ある文書、捏造citation、script・危険URL・外部画像で確認 |
| R11 | 会話全文を1itemへ保存するとDynamoDBの400KB上限に達する | 1メッセージ1item、本文の上限、ページング、原文/manifestはS3 | 大きな履歴、UTF-8 bytes、cursor、他人のcursorを確認 |
| R12 | 利用量通知だけでは高額利用を止められない | 受付時のglobal/user予約、workerの停止確認、token・job・upload・polling上限 | 並行受付で枠を超えず、停止時も履歴・削除が使える |
| R13 | 削除・ログアウトの「即時」という説明が実際のURL・token・バックアップと合わない | 2分の原文URL、アプリ側失効、削除範囲・保存済み履歴・保持期間を定義 | 有効な古いURL、消した資料を引用する履歴、復元を確認 |
| R14 | 障害ログ・追跡サービス・CIの権限から本文やsecretが漏れる | 本文/token/URLの通常ログ禁止、追跡無効、OIDC限定、IAM分離、secret検出 | 実ログ、fork PR、trust policy、CDK権限とモデル入力ログを確認 |

## 残る判断と検証

1. バックエンド言語・実行基盤・DBは推奨案のまま。FastAPI/Lambda/DynamoDBを選ぶ場合、この設計を適用する。GoやECSへ変更する場合はAPI・状態管理・認可を維持して配置部分を再レビューする。
2. リージョン、生成/embeddingモデル、次元数、推論profile、quota、SDK/LangChainの対応版は、実アカウントで検証する。cross-region推論を使う場合はデータの処理先とIAMも確認する。
3. 月額予算とglobal/userの利用枠は未決定。モデル生成・embedding・再試行・polling・ログ・バックアップを含めて見積もる。
4. 招待制、全招待ユーザーのTOTP必須、保持期間はレビューで置いた初期案。公開方法に合わせて確定する。第三者の任意ファイルを受け入れる場合はマルウェア検査を追加する。
5. 同期APIの置換やoutboxで構成が増えるため、先に小さなjobを端から端まで通す。状態・権限・障害回復が成立する前に画面や追加機能を広げない。

## レビューの検証範囲

必須要件の網羅、計画と設計の整合、認証・認可、ファイル処理、非同期・同時処理、RAGの根拠と出力、保存制限、削除・保持、IAM・CI、費用制御を静的に点検した。AWSとOWASPの公式資料で実行制限・失効・署名付きURL・配送・出力処理を確認した。

実行したのは文書レビューと日本語lint。アプリのテスト・CDK synth・AWSデプロイ・セキュリティ攻撃検証は、コードと環境がないため未実施。日本語lintの一覧比率の指摘は、比較表・完了条件の役割を確認し、必要な項目を維持した。

公開の合格条件は詳細設計の「公開前の検証」を通すこと。今回のレビュー完了と公開合格を同一視しない。
