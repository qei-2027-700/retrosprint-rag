# 共通の開発ルール

CodexとClaude Codeで同じルールを使う。共通ルールはこの文書を更新し、ツールごとの入口へ複製しない。

## 作業時に読むもの

最初にルートの [README](../../README.md) で目的と状態を確認する。配置を扱うときは [リポジトリ構成](../architecture/repository-layout.md)、機能を変更するときは対応する `docs/specs/`、重要な判断を扱うときは [ADR](../adr/README.md) を読む。必要な文書だけを参照する。

## 実装と仕様

- backendはhandler・usecase・interface・domain・adapterを分離する。利用側はinterfaceに依存し、domainとusecaseへHTTP・具体adapterの依存を持ち込まない。配置と依存方向は [バックエンドの分離方針](../architecture/repository-layout.md#バックエンドの分離方針) に従う。
- 依頼に必要な範囲を実装・検証し、未使用の抽象化や空ディレクトリを一括作成しない。
- 仕様変更は対象specと受入条件も更新する。重要な技術選定・構成変更はADRへ背景・理由・影響を記録する。
- 採用方針、実装済み、fakeによる検証、実AWSで確認済みの状態を区別する。費用の見積もりを実測や承認済み予算として扱わない。

## 構成変更と不要物の確認

- ツールや配置を変更するときは、manifest・lockfile・workspace設定・共通タスク・CI・手順書の関係を確認し、変更後の利用先がなくなるものをまとめて削除または移動する。lockfileは必要性と保存先を別々に判断する。
- ファイルを残す理由は変更後の構成から説明する。以前使っていたことや将来使う可能性だけを理由に、設定や雛形を残さない。削除後は旧パスの参照と旧構成の設定が残っていないか検索する。
- 依存管理の構成を変更したら、既存のnode_modulesや仮想環境に依存しない一時ディレクトリで、lockfileからの導入を確認する。依存バージョンを維持する変更では、解決結果が変わっていないことも確認する。
- PRの差分を説明するときは、PRのbaseからの全差分と直近コミットの差分を区別する。「追加の不要物はない」などの結論は確認した範囲を添え、起動・型・テストの成功だけで構成全体が適切と判断しない。
- 現在の構成図には実在する管理対象だけを載せる。将来の配置方針は別の節で説明し、構成図に書かれた予定だけを理由に雛形や設定を作らない。

## 初期整備中のGit運用

### Issueの管理

作業は成果単位の独立したIssueで管理する。包括的な親Issueへの紐づけは行わず、必要な仕様文書と具体的な依存Issueだけを参照する。Issue #1は過去の計画記録として扱い、新規Issueの親や最新方針の参照先にしない。目的・開発状況は [README](../../README.md)、最終要件・未決事項・残る完了条件は [開発方針と完了条件](../project-plan.md) を更新する。Issueの終了を、残る要件の実装完了として扱わない。

### コミットとpush

当面はmainへ直接コミット・pushする。作業ごとのbranch作成・PRは必須にしない。変更を意味のある単位でコミットし、変更に応じた検証を行う。GitHub Actionsの導入後はmainへのpushでも検証する。

これは初期整備中の方針とする。整備が進んだ段階でbranch・PR・必須チェックの導入を見直す。mainへのpushだけでAWSデプロイを自動実行する方針はまだ確定しない。

## 検証とデータ

ツールのバージョンと共通タスクはルートの `mise.toml`、配布物の固定は `mise.lock` で管理する。共通の検証入口は `mise run check`。pnpmはFEの依存と固有コマンド、uvはBEの依存を管理する。現在はFE単体のためpnpm workspaceを使わず、pnpmの依存定義・lockfile・install許可設定は `frontend/` 内へまとめる。共通タスク用のルート `package.json` は作らない。

変更に応じたテスト・型チェック・build等を行い、結果と未解決事項を報告する。実行コマンドは各プロジェクトの定義に従い、まだ存在しないコマンドを実行済みとして記録しない。API変更時はOpenAPI・型生成、検索変更時は評価への影響を確認する。

CIはGitHub Actionsを使い、ローカルと同じ検証コマンドを実行する。通常CIはAWS認証・課金なしで実行できる構成とし、実AWS評価やデプロイのworkflowは分ける。詳細は [CIの採用ADR](../adr/0005-github-actions-ci.md) を参照する。

実際の認証情報、私的記録、勤務先の内部情報をコミットしない。公開デモ・評価には公開可能な合成資料を使う。環境設定例はbackend/frontendの `.env.example` に分ける。

## skillの共有

リポジトリ固有のskillは `docs/skills/<skill-name>/SKILL.md` に置く。共通ルールの全文をskillへ複製せず、必要な文書を参照する。個人環境のskillを無条件にコピーしない。

共有skillがない段階では、専用ディレクトリや探索用リンクを作らない。追加するときはCodexの `.agents/skills/` とClaude Codeの `.claude/skills/` から、同じ `docs/skills/` をリポジトリ内の相対シンボリックリンクで参照する。ツール固有の設定や認証情報は共有しない。skillを追加したら両ツールでの検出を確認する。
